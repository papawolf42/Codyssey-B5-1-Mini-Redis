## Q. 아무것도 수정하지 않았습니다. 커밋 전인 해시맵 코드(hash_map.py +64줄, test_hash_map.py +53줄)를 봤고, 테스트 15개는 모두 통과합니다. 계획서의 커밋 2-b 범위와 정확히 맞고, 크기도 116줄이라 150줄 기준 안입니다. 이대로 커밋해도 됩니다.

잘된 점
- _find_node(bucket, key)가 버킷을 인자로 받습니다. put에서 버킷 번호를 한 번만 계산하면 됩니다. 계획서에 적은 _find_node(key)보다 낫습니다.
- 충돌 테스트가 전제부터 확인합니다 (hash_map.py 56줄). 먼저 "k0"과 "k8"이 정말 같은 버킷인지 검사합니다. 나중에 해시가 바뀌어도 이 테스트가 몰래 의미 없어지지 않습니다.
- dict/set을 쓰지 않았고, list는 고정 길이 배열로만 씁니다.

짚을 점

1. capacity가 두 곳에 있습니다. 다음 커밋(3-a, 2배 확장)에서 문제가 됩니다.
   - 36줄은 self.capacity에 저장하고, 42줄 _index는 len(self._buckets)를 씁니다. 지금은 두 값이 같지만, 확장할 때 한쪽만 바꾸면 어긋납니다.
   - 그러면 테스트는 capacity를 보고 통과하는데, 실제 인덱스 계산은 다른 숫자로 하게 됩니다.
   - 방법은 둘 중 하나입니다. _index도 self.capacity를 쓰게 하거나, _resize에서 버킷 배열과 capacity를 같은 자리에서 함께 바꾸는 겁니다.
   - 계획서에도 잘못이 있습니다. 2장은 공개 속성 capacity인데 3-2는 self._capacity로 적어 두었습니다. 2장 쪽(capacity)을 따르면 됩니다.
2. 34~35줄 capacity <= 0 검사는 테스트도 없고 계획에도 없습니다.
   - 평가에서 "이건 왜 있어요?"라고 물으면 "0이면 % 0이 되어 ZeroDivisionError가 나서"라고 답할 수 있어야 합니다.
   - 그렇게 설명할 자신이 있으면 테스트를 하나 붙이고, 아니면 지워도 됩니다. 우선순위는 낮습니다.
3. 이미 커밋된 test_deterministic_and_utf8_range는 이름만큼을 증명하지 못합니다.
   - FNV를 쓰는 이유는 "프로그램을 다시 실행해도 값이 같다"는 점입니다.
   - 같은 실행 안에서 두 번 부르는 비교는 내장 hash()도 통과합니다.
   - 설명할 때 이 테스트를 근거로 들지 말고, 표준 테스트 벡터 3개를 근거로 드세요. 고칠 필요까지는 없습니다.

평가 때 받을 만한 질문 (커밋 전에 말로 답해 보세요)
- 노드에 값만 두지 않고 (key, value)를 함께 넣는 이유는? 같은 버킷 안에서 키를 비교해야 해서입니다.
- 덮어쓸 때 node.data = (key, value)로 통째로 바꾸는 이유는? 튜플은 고칠 수 없어서입니다.
- keys() 순서가 들쭉날쭉한 이유는? 버킷 순서대로 모으기 때문입니다. 나중에 KEYS 출력 순서를 물어보면 같은 답입니다.

이미 커밋된 linked_list
- _is_linked_node 도우미로 방어 조건을 한 곳에 모은 건 좋습니다.
- 다만 다른 리스트의 노드를 넘기면 이 검사로는 막지 못합니다. 그러면 크기(_size)가 어긋납니다.

### 1. 전체 판정: "이대로 커밋해도 합격"
* 크기(`116줄`), 테스트 통과(`15개 OK`), 제약 준수(`dict`/`set` 미사용) 모두 기준에 딱 맞아서 바로 커밋해도 좋다는 뜻입니다.
* `_find_node(bucket, key)`로 해시를 한 번만 계산하게 짠 점, 충돌 테스트에서 `"k0"`과 `"k8"`이 실제로 같은 버킷인지 먼저 확인한 점을 좋게 평가했습니다.

### 2. "짚을 점" 3가지 쉬운 풀이

#### ① `capacity`가 두 군데에 있어서 다음 2배 확장(`3-a`) 때 조심해야 한다
* [hash_map.py](file:///C:/Users/alsgu/Dev/Codyssey/B5-1/mini_redis/hash_map.py#L36-L42)를 보면:
  * 36줄: `self.capacity = capacity` (숫자 따로 저장)
  * 42줄 `_index`: `fnv1a_32(key) % len(self._buckets)` (배열 길이 직접 사용)
* 지금은 둘 다 `8`이라 괜찮지만, 다음 단계에서 2배 확장(`_resize`)할 때 `self._buckets`만 16개로 바꾸고 `self.capacity`를 안 바꾸면 **테스트는 `capacity`만 보고 맞다고 하는데 실제 인덱스는 엉뚱한 크기로 계산하는 버그**가 생길 수 있다는 경고입니다.
* *(해결은 아주 간단합니다: `_index`도 `self.capacity`를 쓰거나, 아예 `capacity`를 `@property`로 `len(self._buckets)`를 돌려주게 만들면 둘이 어긋날 일이 없습니다.)*

#### ② 34~35줄 `if capacity <= 0:` 검사는 왜 넣었는지 말할 줄 알면 된다
* 34~35줄에 넣은 `if capacity <= 0: raise ValueError(...)`는 요구사항에 없던 방어 코드입니다.
* 평가관이 *"왜 있어요?"*라고 물으면 **"0이 들어오면 `% 0`에서 `ZeroDivisionError`가 나고, 음수면 버킷이 0개가 되니까 막아뒀습니다"**라고 대답하면 되고, 설명할 자신 없으면 지워도 무방하다는 뜻입니다.

#### ③ `test_deterministic_and_utf8_range`의 한계
* 같은 프로그램 실행 안에서 `fnv1a_32("한글:키")`를 두 번 불러 같다고 비교하는 건 파이썬 내장 `hash()`도 똑같이 통과합니다.
* 그러니 평가에서 **"프로그램을 껐다 켜도 값이 항상 같다"는 근거**로는 이 테스트 대신 **`test_standard_vectors` (`0x811C9DC5`, `0xE40C292C`, `0xBF9CF968` 고정 숫자 비교)**를 말하라는 조언입니다.

### 3. 평가 대비 예상 질문 3개 요약
1. **노드에 `(key, value)`를 같이 넣는 이유?** → 충돌 시 같은 버킷 안의 여러 노드 중 내 키를 찾아 비교해야 해서 (`node.data[0] == key`)
2. **`node.data = (key, value)`로 통째로 덮어쓰는 이유?** → 파이썬 **튜플은 수정 불가(immutable)**라서 `node.data[1] = value`처럼 일부만 바꿀 수 없어서
3. **`keys()` 순서가 입력 순서와 다른 이유?** → 입력 순서를 기억하는 게 아니라 **버킷 배열 0번~끝번 순서대로** 꺼내 모으기 때문 (나중에 `KEYS` 명령어 순서와도 같은 이유)
